System walkthrough · from browser request to calendar event

Prayer Times
Automation

A detailed, step-by-step tour of the backend: OAuth onboarding, timetable retrieval, OCR decisions, date inference, Google authorization, event reconciliation, cron behavior, and failure handling.

Based on the current workspace code: app.py, create_schedule.py, drive_timetable.py, timetable_dates.py, and config.json.

Two separate Google Calendar write paths: a member's OAuth identity writes to that member's chosen calendar; a service account writes to the central Master Calendar during the all-members cron run.

01 · Orientation

What the backend does

It turns the latest timetable image into a validated set of prayer times and dates, then reconciles generated events into one or more Google calendars.

Web / onboarding

Flask presents OAuth endpoints. A member grants calendar access; the app stores an encrypted refresh token and starts an initial sync.

Schedule engine

Drive fetches the newest timetable image. OCR and date logic produce validated values. The scheduler creates, updates, or skips events.

Persistence / operations

Supabase stores member linkage and sync state. Render hosts the app and scheduled job; runtime secrets supply credentials.

Important scope boundary: the code shown implements a Flask web app and a command-line scheduler. The actual cron schedule/command is configured in the hosting platform, not in these Python files.

03 · Process map

Two entry points, one schedule engine

Member's first connection

  1. Browser opens /connect_google.
  2. Member grants OAuth consent.
  3. Callback validates the response and saves the encrypted token.
  4. Scheduler runs for that member ID.
  5. Calendar events are reconciled in that member's calendar.

Scheduled weekly run

  1. Host launches create_schedule.py --all-members.
  2. Scheduler downloads and processes the latest timetable.
  3. Master Calendar is synced first.
  4. Connected Supabase members are synced one by one.
  5. Any counted failure makes the run exit with an error.

Both routes call the same date/OCR builder and sync_member routine, but choose credentials and calendar destinations differently.

04 · Startup and configuration

What must exist before the work starts?

Application setup

  • Flask uses FLASK_SECRET_KEY for signed sessions.
  • Fernet requires TOKEN_ENCRYPTION_KEY.
  • Supabase client requires URL and service-role key.
  • Google OAuth client config comes from a Render secret file or JSON environment variable.
  • Hosted REDIRECT_URI must start with HTTPS.

Schedule settings

  • timezone: local event timezone (Europe/Berlin).
  • public_calendar_id: Master Calendar destination.
  • friday_replaces_zohar: Juma policy.
  • reminder_minutes: per-prayer popup offsets.
  • OCR runtime: Tesseract plus English/German language data.

The Dockerfile installs Python dependencies and the Tesseract executable/languages. Render injects runtime secrets and invokes Gunicorn or the separate cron command.

05 · OAuth begin

Member presses “connect Google”

1

Clear prior flow state

session.clear() removes stale OAuth session material, then the session is marked permanent with a 15-minute lifetime.

2

Load OAuth client

Use GOOGLE_OAUTH_CLIENT_JSON if present; otherwise load the client-secrets file. The secrets must describe a web client.

3

Request permissions

Ask for Calendar, Calendar events, verified email identity, and OpenID. Request offline access so later scheduled jobs can refresh credentials.

4

Protect the round trip

Generate OAuth state and a PKCE code verifier. Keep both in the secure session; redirect the browser to Google.

Cookie protections include Secure, HttpOnly, and SameSite=Lax. Responses also set no-store and no-referrer headers.

Code: app.py, /connect_google; OAuth scope constants and application settings.

06 · OAuth callback

Google returns to /oauth_callback

  1. Read expected session state, returned query-string state, and PKCE verifier.
  2. Reject missing state/verifier or a non-matching state (constant-time compare).
  3. Consume state/verifier before continuing, so the callback cannot reuse them.
  4. Handle cancellation, missing authorization code, and token-exchange errors.
  5. Exchange the code with the same OAuth client and PKCE verifier.
  6. Require Calendar scope and a refresh token for future background updates.
  7. Call Google userinfo; require stable account ID, email, and verified email.

If Google does not return offline access / a refresh token, the app rejects the connection because a scheduled job cannot rely on the member being present to sign in again.

Code: app.py, /oauth_callback.

07 · Member persistence

Store enough to reconnect—without storing a plain token

Google refresh token
→
Fernet encrypt
→
Supabase upsert

Saved / updated fields

Stable Google subject ID, verified email, encrypted refresh token, connection_status="connected", initial_sync_pending=true, and update timestamp.

Reconnect behavior

Upsert is keyed by stable Google subject. On an existing record, the code intentionally leaves the selected calendar_id, creation timestamp, and last-sync timestamp alone.

The app queries Supabase for the saved member row's internal ID. It then invokes main(member_id=...) for the immediate initial sync.

The success page is rendered even if that inner initial-sync call raises: the callback logs the exception and continues. Therefore, verify the logs/calendar, not only the page, when confirming first-time event creation.

08 · Scheduler begins

Every sync first constructs the timetable

Whether called after login or by cron, main() begins by calling build_prayer_times_and_dates() before it selects destinations.

A

Load config

Read JSON relative to the source directory; construct the configured timezone; get current local year/date.

B

Fetch image

Drive service account lists the newest image directly inside the configured folder; retrieve file bytes in memory.

C

Prepare OCR

Apply image orientation, convert to RGB, then create a grayscale, 3× enlarged, contrast-adjusted copy to read date text.

On Windows the code points Tesseract at its standard install path; on the Linux container it invokes tesseract from PATH.

Code: create_schedule.py, build_prayer_times_and_dates(); drive_timetable.py, fetch_latest_timetable().

09 · Drive lookup

How “latest timetable” is selected

  1. Require GOOGLE_APPLICATION_CREDENTIALS; load the service-account JSON at that path.
  2. Request the read-only Drive scope.
  3. Query the configured folder for non-trashed image MIME types.
  4. Order by createdTime desc, request one file, including shared-drive support.
  5. If no image exists, raise an explicit error mentioning folder/access checks.
  6. Download chunks into BytesIO; rewind and return the stream plus file metadata.
  7. Close the Drive service in a finally block; close the stream if download fails.

This selects the newest created image directly inside the folder, not necessarily a recursively nested file and not a file chosen by filename.

Code: drive_timetable.py.

10 · OCR strategy

Read prayer times with layered safeguards

Tier 1 · fixed prayer bands

Crop six proportional vertical bands from the original image. Use the central horizontal region, grayscale, 4× scale, autocontrast, white border, and Tesseract single-line mode. Whitelist digits and colon. Accept only a strict valid HH:MM.

Tier 2 · whole-image scan

Parse explicit prayer/time pairs on the same OCR line. A second scan uses 4× resize, thresholding to reduce a pale watermark, token coordinates, and confidence scores.

Tier 3 · targeted fallback

If a prayer is still unresolved, crop its full-width row with padding, scan several image-threshold variants, and require a clear repeated vote.

If a prayer still has no safe, unambiguous time, raise an error and stop before writing any calendar events. Do not silently invent or accept a dubious time.

Code: extract_original_whole_image_times(), extract_second_whole_image_times(), select_whole_image_fallback(), and extract_flexible_prayer_row_time().

11 · OCR details

How the fallback scans decide what counts

  • Label normalization: remove non-letters and lowercase; map variants such as Fair/Fair-like Fajr, Zuhr/Dhuhr, Asr, Isha, Jumma/Jumuah to canonical names.
  • Second scan geometry: retain nonempty OCR tokens, their bounding boxes, and confidence; labels under confidence 30 are ignored.
  • Same-row association: only inspect tokens to the right of a label whose vertical centers are close.
  • Split-time assembly: try one, two, or three neighboring tokens to support 06:40, 06: + 40, or 06 + : + 40; reject low-confidence or widely spaced pieces.
  • Band retry: if any of six expected prayers has zero or multiple candidate times, locate reliable Fajr and Juma anchors in the same column, crop the intervening full-width band, and scan it as a text block.
  • Consensus selection: union original/second whole-image candidates. More than one distinct time means disagreement and rejection; exactly one is accepted.
  • Flexible row vote: scan the row in contrast plus thresholds 145, 180, 210. A valid time must win uniquely with at least two votes. If it disagrees with any whole-image candidate, reject it.

The rectangle scan is preferred; fallback logic is only used when its strict parse or time validation fails.

12 · Date text parsing

OCR date → typed endpoint candidates

Recognized vocabulary

German weekdays and month names, plus abbreviations/variants: e.g. Mär/Mar/Maerz, Okt/Oct, Dez/Dec. Date patterns allow optional punctuation and optional four-digit year.

Endpoint role

Explicit ab marks start; bis zum or zum marks end. Without a marker, Saturday/Sunday is treated as start and Friday as end. Other unmarked weekdays are not guessed.

  1. Find dates with optional marker and weekday; ignore unrelated unmarked dates.
  2. Record role, weekday, day/month/year, and matched text.
  3. Also detect marker + weekday without a numeric date (weekday-only endpoint).
  4. Reject conflicting weekdays for the same role.
  5. Convert month text; reject unknown months.

Code: parse_timetable_endpoints(), _role_for(), _weekday_only().

13 · Year inference

Resolve missing years without guessing blindly

  1. If OCR supplies any explicit year, use those as reference years; otherwise use the configured timezone's current year.
  2. For each reference year, consider the previous, same, and next year (within valid calendar-year limits).
  3. For every date endpoint without an explicit year, construct actual calendar dates in those candidate years.
  4. Discard impossible calendar dates (such as an invalid month/day) and dates whose weekday disagrees with OCR.
  5. For multiple endpoints with the same role, intersect candidate sets: every start clue must agree on the same start; every end clue must agree on the same end.
  6. If candidates become empty, reject the OCR as contradictory rather than choosing the nearest-looking date.

Example: “Saturday, 17 Oct” with no year is tested against adjacent candidate years; only years where that date really is Saturday survive.

Code: _endpoint_date_candidates(). Date candidate creation is separate from range construction.

14 · Range construction

How partial or complete ranges are assembled

Start + end found

Pair candidate start/end dates where end is on or after start and no more than seven days later—so the inclusive range is at most eight days.

Only end found

First try day after last event as the start if the span is 0–7 days and matches a valid expected start pattern. Otherwise infer a standard or DST-transition range backward from the end.

Only start found

Infer forward from the start using the regular or DST-transition pattern. If no explicit start exists, a history date can supply “last event + 1 day.”

Every possible range is then filtered: 1–8 inclusive days, start weekday match if known, end weekday match if known. If several remain, keep those closest to the reference date (zero distance when it lies within a range).

Zero valid ranges means inconsistent OCR/history; multiple equally-near ranges mean ambiguity. Both raise an error instead of selecting a week arbitrarily.

Code: resolve_timetable_dates().

15 · Week-length inference

Regular weeks and daylight-saving transition weeks

Regular timetable

  • A Friday end normally means start six days earlier: Saturday–Friday, 7 inclusive days.
  • A Saturday start normally means end six days later: Saturday–Friday.

Transition-week exceptions

  • Spring Sunday is the last Sunday in March; autumn Sunday is the last Sunday in October.
  • Saturday before transition Sunday can be the end of an 8-day period starting the prior Saturday.
  • Transition Sunday can start a 6-day period ending Friday.
  • A Saturday immediately before transition Sunday is deliberately not treated as an ordinary Saturday start.
End = Saturday before DST Sunday  → start = end − 7 days (8 inclusive)
End = Friday after DST Sunday     → start = DST Sunday (6 inclusive)
Start = Saturday 8 days before    → end = day before DST Sunday
Start = DST Sunday                → end = following Friday

For dates near transition Sundays, the backward end-inference helper refuses ambiguous in-between days rather than falling through to a normal Friday rule.

16 · Date-history fallback

OCR cannot resolve dates? Consult that calendar's own history

  1. Query events up to ten years back, paging through results.
  2. Keep only known prayer summaries and descriptions containing the app marker Prayer Timings Automation:.
  3. Read the event's all-day date or convert its date-time into the configured local timezone.
  4. Take the latest matching prayer-event date.
  5. Use that date as history to infer the next timetable block.

With readable history

Try “last event date + 1” as the next start; validate against the OCR end/weekday and known week patterns.

Without readable history

If OCR also has no usable date, stop. Do not make up a start date. Google/auth/API errors during history lookup are converted to an explicit fallback failure.

This check happens per target calendar, because member and Master Calendar event histories can differ.

17 · Destination selection

Same sync function, separate identities

Member record (OAuth)

  1. Decrypt that row's refresh token.
  2. Build OAuth credentials with client ID/secret, token endpoint, and requested scopes.
  3. Refresh the access token.
  4. Check saved calendar ID; if missing/invalid, list calendars where role is owner/writer.
  5. Prefer prayer-related names (prefix match first, then contained prayer/salah/namaz/salat); else use primary.

Master mock record (service account)

  1. Use Render secret path first; local JSON fallback second.
  2. Load service-account credentials with Calendar scope.
  3. Build Calendar API client.
  4. Use configured public calendar ID directly—no calendar search.
  5. Do not write a fake Master member into Supabase.

The member's token cannot write on behalf of the Master service account, and the Master service account does not impersonate the individual member.

18 · Cron member selection

Which targets does each invocation process?

Weekly: --all-members

Fetch all rows with connection_status="connected", sorted by ID and paged 500 at a time. Enable Master Calendar sync regardless of whether the member list is empty.

OAuth callback

Fetch one row matching internal member ID and connected status. No Master Calendar target is added to this path.

Invalid invocation

Passing both modes is rejected; passing neither all-members nor a member ID is rejected.

If Supabase member lookup fails during weekly cron, the code records a failure but still attempts the Master Calendar sync. Individual member sync is unavailable for that run.

A pending-members query/helper exists, but the weekly all-members selection shown here uses all connected rows; it does not limit the weekly run to only pending users.

19 · Schedule generation

Turn one timetable block into event payloads

  1. Iterate each inclusive calendar date from start through the resolved day count.
  2. Start with Fajr, Zohar, Assr, Maghrib, Ishaa.
  3. On Friday (weekday 4), either replace Zohar with Juma or append Juma, based on config.
  4. Combine each date and OCR time in the configured timezone.
  5. Set end time five minutes after start.
  6. Build the summary, explanatory description, timezone-aware start/end, and a popup reminder using that prayer's configured offset.
  7. Hash calendar ID + ISO date + canonical prayer name for a stable event ID.
event key = "prayer-timings|calendar_id|YYYY-MM-DD|Prayer"
event ID  = SHA-256(event key)

A distinct ID per calendar prevents the Master Feed's event identity from colliding with an individual calendar's identity.

20 · Reconciliation

Create, skip, update—or replace a deleted event

Insert

No ID conflict: create event using deterministic ID.

Skip

Existing confirmed/tentative event matches managed fields exactly.

Patch

Existing live event differs: patch summary, description, start, end, reminders only.

Replace ID

Existing ID is cancelled/deleted (including lookup 410): derive another hashed ID and retry, up to 50 generations.

Matching checks summary and description; parses and compares start/end instants and timezone; compares default-reminder mode and sorted reminder overrides.

If lookup after an ID conflict is uncertain for a reason other than deleted/410, re-raise. The code intentionally avoids making a possible duplicate based on an uncertain read.

Only app-managed fields are patched so unrelated event fields are preserved.

21 · Retries and persistent state

Transient trouble versus account repair

Retryable Calendar API errors

Retry HTTP 429, 500, 502, 503, 504, plus HTTP 403 only when the error identifies a rate-limit condition. Up to 8 tries; exponential delay starts at 1 second and doubles per retry.

Invalid member refresh token

For a confirmed invalid_grant, mark that member reconnect_required. The user needs to reconnect Google; transient errors are not automatically mislabeled as revoked consent.

On a successful member sync, save the resolved calendar ID, clear initial-sync-pending, set last-synced time, and leave connection status connected. Master sync skips this database update because it has no real member row.

Track outcomes as created, updated, skipped. A member's thrown exception increments failure count, is logged, and processing proceeds to later selected members.

22 · Completion and failure

How the cron decides whether it succeeded

Build timetable
→
Master sync (weekly)
→
Member syncs
→
Aggregate counts
→
Exit 0 or raise
  • OCR/date/image-building errors happen before destination syncing and abort the run.
  • Master exception increments failure count, is logged with token-like values redacted, then member loop still proceeds.
  • Individual member failures are counted; reconnect-required state is updated only for confirmed invalid grants.
  • Summary prints selected/successful/failed; any nonzero failures cause RuntimeError and a nonzero process exit.
  • Zero connected members is not itself an error: a weekly run still tries the Master Calendar.

Success output and Render job status are separate from the member browser's OAuth success page.

23 · Safety model

Where the guardrails are—and are not

Present in code

  • HTTPS required for hosted OAuth redirect.
  • OAuth state + PKCE verifier checked before token exchange.
  • Secure session cookie flags and sensitive response cache/referrer headers.
  • Refresh token encrypted before Supabase storage.
  • OCR/date ambiguity fails closed; uncertain event lookup avoids duplicates.
  • Central Master error logs redact token-like values.

External setup still required

  • Keep Render credentials/secrets private and rotate exposed keys/tokens.
  • Grant Drive folder Viewer access to the Drive service account.
  • Grant the Master Calendar edit access to its service-account email.
  • Keep the Fernet key stable; changing it makes stored member tokens undecryptable.
  • Configure cron schedule and command correctly in the host.

The local workspace includes a service-account filename. Never copy secret JSON contents into a slide, commit, issue, or public log; the presentation deliberately contains no credential values.

25 · Full sequence

From first request to last event

  1. Website redirects the member to the Flask OAuth endpoint.
  2. Google consent returns a code; callback verifies session state and PKCE.
  3. App validates Google identity and permissions; encrypts refresh token; upserts Supabase.
  4. Initial sync—or later weekly cron—loads config and fetches newest timetable image from Drive.
  5. OCR extracts candidate week and six prayer times using primary scans and controlled fallbacks.
  6. Date resolver validates year, weekdays, range length, transition patterns, and/or per-calendar history.
  7. Choose member OAuth destination or Master service-account destination.
  8. Generate deterministic event IDs and timezone-aware payloads; reconcile existing Google events.
  9. Persist successful member sync state; summarize outcomes; exit successfully only if no failures were counted.

Core reliability principle: uncertain inputs (OCR, dates, authorization, deleted-event lookup) should stop or surface an error rather than silently creating a plausible but incorrect schedule.

End · Takeaways

Three ideas to remember

1

Credentials are intentionally split

Member OAuth writes to personal calendars; service-account identity writes to the central feed; Drive access is its own service-account operation.

2

Inputs are validated before writes

OCR uses layered corroboration; dates must resolve unambiguously; calendar history is the fallback, not a license to guess.

3

Sync is designed to be repeatable

Deterministic event IDs and managed-field comparisons make reruns create, update, or skip; failures are counted and surfaced to cron.
